# KV ring opt-in: adversarial source review (2026-11-14)

**Scope:** read-only inspection of worker4's in-progress `distributed/pp2_fwd.cu`, `pp2_fwd.hpp`, `distributed/tests/test_sliding_kv_optin_contract.py`; `distributed/pp2_batch.cu` and `serving/server.cpp` read strictly for caller contracts. No CUDA compilation, GPU/model inference, SSH/network, running service or production edits. This is **not** GPU numeric parity, a latency measurement, or acceptance of production context >8192.

## Findings ordered by impact

1. **BLOCKER for actual serving integration; NOT a ring-slot off-by-one.** `pp2_fwd.cu:1603-1609` requires the opt-in decode state to be allocated at *exactly* capacity 8192; `server.cpp:1070-1075` and `pp2_batch.cu:313-316` allocate `prompt.size()+max_new_tokens-1`, so most requests under the global opt-in fail state initialization. More importantly `server.cpp:124,1551-1554`, `pp2_batch.cu:146-152,188-192,304-314` prohibit total requested decode beyond 8192. Even if a request has computed capacity 8192, its final generated token does not require a decode at absolute pos 8192 (`server.cpp:1070-1072`). Therefore the production HTTP/scheduler routes **cannot execute the wrap branch**. This may be intentional while the feature is experimental, but must be stated plainly and independently gated before calling the feature usable in serving. Smallest later integration: an explicitly opt-in logical total-length bound distinct from the fixed **physical** allocation `decode_init(...,8192)`, with admission calculated from physical KV bytes, and a separate cap on absolute positions below `1<<20`. Keep the default context=8192 behavior unchanged. Do not change caller ownership as part of this review.

2. **BLOCKER for numeric acceptance: GPU execution and model parity remain unproven.** The Python CPU deque in `test_sliding_kv_optin_contract.py:33-112,245-345` models desired semantics; it never calls the CUDA kernel. `validates_source_code()` at :121-179 checks literal source substrings and ordering but cannot prove that compiled CUDA evaluates the intended operands or respects device stream behavior. For example, change only `tmp[tid]=qv*kv` to `tmp[tid]=qv+kv` at `pp2_fwd.cu:1282`: the listed source assertions do not inspect this expression and the independent deque oracle continues to pass, yet every attention score is wrong. Preserve these tests as useful static/CPU contracts, not a CUDA parity witness. Required later gate: capture logits and layer-level K/V, GDN S/CS, attention output for 8191/8192/8193 and after a second wrap against an independently computed reference; separately compare prefill-seeded state at T8192 and token-by-token warm-up. Compiling successfully is insufficient.

3. **High throughput regression risk after first wrap, no benchmark evidence.** Each full layer at `pp2_fwd.cu:1525-1556` synchronizes its stream **twice** (after the attention kernel and after the two copies), hence 16 full layers mean 32 synchronous waits for every token >=8192, on top of GPU0/GPU1 host-event handoffs at :2098-2109 and :2127-2132. The kernel at :1277-1306 iterates serially through 8192 positions with repeated block barriers. This is correct-looking but can dominate token latency and aggregated multi-user throughput. Device events/stream ordering already give a potential route to enforce read-before-eviction with fewer host waits; any optimization must retain the hard read-before-write dependency and poison on *asynchronous* failure. Measure latency and N1/N2/N4 aggregate before making performance claims.

4. **Minor fail-closed contract mismatch on non-mutating public guard failures.** Header `pp2_fwd.hpp:78-85` says a failed sliding decode must never be resumed. `decode_step()` returns on invalid position or unavailable workspace at `pp2_fwd.cu:2142-2154` *before* poisoning; a subsequent valid call can still proceed. This does not establish GPU state corruption because these guards precede mutation, and the async preflight correctly poisons under its request lock (`:2052-2065`). Either narrow header language to failures *after mutation / preflight* or enforce a documented terminal-error policy while preserving thread safety. Do not treat an early invalid-position rejection as proof of a partial GPU write.

5. **VRAM postcheck misses stream setup.** `pp2_fwd.cu:1628-1648` computes GDN+KV+workspace and preflights each device, then `:1684-1693` checks the 15-GiB ceiling **before** `async_prepare` allocates streams/events/pinned transfers at `:1698-1704,1367-1385`. Thus the advertised 15-GiB postcondition is unverified after async resources are created. It is a headroom/accounting gap; without a GPU allocation trace, no actual over-limit incident is proven. A final per-device `cudaMemGetInfo` check after `async_prepare` would close this gap.

6. **CPU test cost and coverage.** The wrap test loops through every position up to 16385 and calls both `chronological_attention()` and `stage_attention()` on **every** iteration (`test_sliding_kv_optin_contract.py:249-269`). Both materialize a history/window of up to 8192, making the Python test O(8192²) in total copied elements although comparisons are made at just 11 checkpoints. Evaluate the full windows only at checkpoints, and keep cheap stage/commit for intermediate positions. Static source tests currently do not inspect scratch pointer aliasing, two-device event use or GPU numeric results.

## Source contracts confirmed by inspection

- **Window/order:** At absolute `p`, `sdpa_gqa_ring_decode_k` sets `count=min(p+1,capacity)`, reads positions `p-count+1 .. p-1` via `slot=absolute%capacity`, and reads the just-computed `p` directly from `d_K1/d_vv` (`pp2_fwd.cu:1266-1306`). Thus at 8192 the required window is 1..8192, slot 0 still retains old token 0 during attention; at 8193 the window is 2..8193. Subsequent `cudaStreamSynchronize(stream)` precedes both `cudaMemcpyAsync` overwrites of `slot=p%8192` (`:1525-1556`). These are source-level properties, not runtime assertions.
- **RoPE:** Both Q and K receive the original absolute `pos` (`:1194-1229,1522-1523`); no modulo or origin reset on wrap. `sliding_kv_step_preflight` rejects pos >= 1048576 and enforces all 16 `klen[li]==pos` (`:2020-2045`), avoiding signed-int overflow at the configured bound. Each completed layer increments klen to L+1 (`:1589`).
- **Per-layer device/address:** 16 full layers (`li%4==3`) have distinct FP32 KV `cudaMalloc` allocations; eight per device by split at 31 (`:1653-1666`). 48 GDN layers preserve S and CS indefinitely: `conv_decode_k` and `gdn_step_cuda` advance their persistent state (`:1182-1193,1434-1441`). There is **no** GDN truncation to the last 8192 tokens, and exact equivalence to recomputing a truncated prompt cannot be claimed.
- **Staging, aliasing, synchronization:** `d_K1` and `d_vv` live in the per-device, per-request workspace at distinct offsets from `d_att` (`:1495-1516`); Kc/Vc are separately allocated (`:1656-1659`). The async path uses one per-state mutex, one stream/event per device, and three distinct pinned host buffers (`:1321-1385,2048-2139`). GPU0 D2H finishes before GPU1 H2D; GPU1 logits completion precedes host return and poison clearing. `decode_free` drains both streams before freeing K/V, S/CS, workspaces and staging (`:1342-1365,1710-1740`). This is correct at the API's caller-owned lifetime boundary; do not concurrently destroy a state while another thread is entering `decode_step`.
- **Initial 8192 seed:** Internal opt-in can initialize state with capacity 8192, seed 8192 tokens in <=64 chunks (`:1891-2013`; requires separate `HERMES_PP2_CHUNKED_PREFILL=1`), and issue its first ring step at pos8192. Chunked full attention writes and reads linear caches through the prefix at `:618-679`; seeded GDN conv tails are passed from chunk to chunk at `:525-538`. This is the missing real parity test path, not proof that parity holds.
- **Bounds:** KV per GPU = 8 full layers * K+V * 8192 * 1024 * 4 = **512 MiB**; plus ~74.81 MiB of 24 GDN S/CS and ~0.56 MiB GPU0 / ~1.53 MiB GPU1 decode workspace, before allocator/stream overhead (`:1628-1636`). Kernel dynamic shared memory = (8192+256)*4=**33,792 bytes** (`:1529`), inside a 48-KiB per-block envelope. Physical KV remains bounded while absolute positions increase.

## Deterministic falsification scenarios for owner/prime

1. **Small-window CPU mapping:** Use capacity 4 or 8 and 16 independent full-layer identities. Stage each token `p=0..3*capacity+2`; before committing, compare chronologically read keys/values with a separately written deque, verify the to-be-reused slot still contains `p-capacity` and verify there is no duplicate/omitted oldest token after wrap. Encode distinct K/V values per layer; split eight layers to each simulated device.
2. **Boundary + seed:** Seed a full prefix in chunks (e.g. 8128 + 64), check Kc/Vc slots and 48 recurrent S/CS against stepwise reference, then continue positions 8192, 8193, 16383, 16384. Compare post-token logits and layer hidden values, not just lengths/physical slots. A CPU model alone cannot prove CUDA numeric agreement.
3. **Injection/poison:** Force errors before attention, between attention and K copy, after K copy before V copy, and during GPU1/event completion; cancel once while GPU0 is active and once after GPU0 handoff. Expected: request cannot return usable logits on partial failure, all subsequent steps are rejected, and stream drain finishes before any state buffers are freed. A deterministic mocked backend/scheduler is suitable for lifecycle; real CUDA asynchronous failures need separate GPU tests.
4. **Invalid/out-of-order requests:** Try pos8191 when klen=8192, skip to pos8193, pos1048576, and concurrent same-state steps; verify rejection. Decide whether validation-only errors must poison and make header, implementation and test agree.
5. **Mutation test for source gates:** Mutate only the CUDA attention multiply to addition without changing any literal strings tested by `validates_source_code`; the current CPU/static suite should fail to detect this defect. Add a native kernel cross-check in the GPU gate.
